# Security and trust

What you are agreeing to when you run this, or join a service. The short version: an app that can act on your photos has to be trusted, so it is built to ask for as little as possible, show people what it does, and make leaving easy.

## What a key can do

An Immich API key cannot be limited to one tag or album. So a sender's key can read and download any photo in that account, and, if the sender chose **move**, delete any photo too. The app only ever acts on photos tagged for a service, and the key is never shown to anyone. If the sender chose **keep my originals** (the default), the key is created **without any permission to delete**.

A sender who links an album to a service ([Using it](using.md#handing-over-a-whole-album)) gives their own key one more permission, `album.read`, added with their own login. It lets the app list the photos in that album; it cannot change, share or delete albums. Photos that other people own are never handed over.

The receiver's key can upload photos, read the receiver's library and add tags. By default (`RECEIVER_DELETE=on`) it can also **move photos to the receiver's trash** (`asset.delete`), which is what makes copies that expire and a sender's "take back the last hand-over" possible. The app uses it for nothing else: it moves to the trash only copies it handed over itself, and only those that were never filed in an album, and it never deletes for good (the receiver's trash keeps them for as long as Immich does). An administrator who does not want a key that can do that sets `RECEIVER_DELETE=off`: keys are then made without it, and a key that has it loses it when its owner next opens the page (see [Settings](settings.md)). If the service puts arrivals in an album, the key can also find, create and add to albums (`album.read`, `album.create`, `albumAsset.create`); it still cannot rename, share, empty or delete an album, and the app only looks at albums the receiver owns, never at ones shared with them.

Each key is named `handoff: <service>` in the owner's own Immich settings, so people can see exactly what exists and delete it whenever they like. Deleting it ends the connection at once: Immich refuses the key, the app notices and pauses, and no photo is touched.

## Bridges: a receiver on another server

A [bridge](using.md#receiving-on-another-immich-server) makes the app hold a key to a library on a server **it does not run**, and connect to an address a stranger typed. Both are risks, so each is made as small as it can be. Bridges do not exist until an administrator sets `BRIDGE_ENABLE=true`.

**What the key can do.** `user.read`, `tag.create`, `tag.asset` and `asset.upload`: it can upload a photo and put a tag on it. It cannot read or search the library, download anything, list albums, tags, people or keys, and it cannot change itself. The receiver may add one optional permission, `asset.delete`, so that a sender can take a hand-over back: the app then moves the copies it handed over (the ids it remembers, nothing it looks up) to the receiver's trash within 24 hours, never deleting for good. It cannot tell whether the receiver has filed one in an album, so that one goes to the trash too. The permission is read from the key at every pass and before a take-back, so removing it ends the feature at once. This was checked against a real Immich, not assumed. The app refuses a key with more (the optional permission aside), and a key with less, when a bridge is made and again at every pass, so it never holds power it does not need. The receiver makes the key in their own Immich, sees what it can do, and deletes it whenever they like: Immich then refuses it at once, the app stops, and nothing is lost. What the receiver can see of a sender is the photo (with the details Immich carries in the file) and the tag `from/<name>`; no account detail is sent. What the sender sees of the receiver is the name they chose, the version of their Immich and whether the connection works; never their library.

**Where the app will connect.** Only to an address that starts with `https://` and whose name resolves to **public** addresses. Loopback, private, link-local (which includes the cloud metadata address), unique-local IPv6, carrier-grade NAT, multicast and reserved ranges are refused, an address written as IPv6 is judged as the IPv4 address it is, and **the judgement is made again on the real connection**, so a name that changes between the check and the connection cannot slip through. Redirects are never followed (a server that redirects is treated as unreachable, and `doctor` says where it points). Proxies from the environment are ignored. Calls give up quickly on silence. A page that refuses an address says only that it is not one the app may connect to, whether or not something answers there, so it cannot be used to map your network. Attempts on the invitation page are limited to 10 an hour per address and 20 an hour per link (see [`DROPBOX_CLIENT_IP_HEADER`](settings.md)). `BRIDGE_ALLOW_PRIVATE=true` lifts the address rules and allows `http://`, for people who run both servers themselves behind a VPN; with it, **an address someone types can make the app reach into your own network**, so leave it off otherwise.

**What the app never does.** It never calls `GET /users` on a remote server (any key with `user.read` can list every user and email there), and it keeps nothing a remote server returns beyond its version. The key is stored encrypted like every other key and never shown.

**The invitation link** names the service and the person who offers it, and nothing else. Anyone who has it can connect their own server to the service until it is used, replaced or a week old; a link that is unknown, used or old gives the same page.

## Drop boxes

A [drop box](using.md#drop-boxes-photos-from-people-who-do-not-have-immich) is the one part of the app that is open to people who are not signed in to anything, so it is built to do as little as it can.

- **What a link allows.** Whoever has it can send photos and videos to its owner's library, up to the limits the owner set, until it expires, is paused or is revoked. That is all. It cannot list, read, download, change or delete anything, and a guest never sees what was stored, not even their own files.
- **The key.** A drop box has a key of its own in the owner's account, named `handoff: <name> (drop box)`, made with the owner's own login and holding five permissions: `user.read`, `tag.read`, `tag.create`, `tag.asset` and `asset.upload`. A box that files into an album also has `album.read`, `album.create` and `albumAsset.create`, and a box that lets guests take back what they sent also has `asset.read` and `asset.delete`: that is the one kind of box whose key can read a photo's tags and move a photo to the trash (the app only does it for a photo the same guest sent that still carries the box's inbox tag, and only to the trash). It cannot read a photo back, delete one, or change, share or delete an album. Revoking the box deletes it.
- **The link.** It holds 256 bits of randomness, so it cannot be guessed. A link that is unknown, paused, past its end or revoked gives the same answer, so nobody can tell which it was. The page sends `no-referrer`, so the link does not leak to other sites, and is never cached.
- **What is checked.** The first bytes of each file decide what it is, never its name or what the browser says. Only photos and videos Immich can show are stored; the stored name is cleaned. Files are streamed to Immich and never kept on the app's disk or in its memory. Size limits are enforced while the file streams, so an oversized file is cut off, not read to the end.
- **Limits against abuse.** Per guest: 30 requests in ten minutes and 300 files an hour. Per box: four uploads at once, and an automatic pause after 1000 files or 200 refusals in ten minutes. A password, if set, is stored as a salted PBKDF2 hash and slows guessing down to five tries per ten minutes.
- **What is remembered about guests.** A short one-way mark made from the link and the guest's address together, shown in the log. The address is not stored, the mark is useless outside its box, and the log keeps at most 200 entries per box. The limits above keep their counts in memory only. Behind a reverse proxy the app sees the proxy's address unless `DROPBOX_CLIENT_IP_HEADER` names the header that carries the real one; without it all guests count as one for the per-guest limits (the per-box limits still hold).
- **Files that wait for approval** are kept on the server's disk, in the data folder (`dropbox-pending`, mode 0700), after the checks above, and nowhere else. They are shown only to the owner and the co-hosts who manage the box, as images with a content security policy that allows nothing to run, and are deleted when approved, rejected, after two weeks, or when the box is revoked. They are not in backups.
- **Photos sent from a phone** arrive in pieces and wait on the server's disk, in the data folder (`phone-uploads`, mode 0700, one folder for each person, not in backups), until the file is whole. Only a person signed in to Immich can start, send or finish one (their own cookie and the cross-site header, as for every change on the page), and only their own uploads are visible to them; an upload's name is a random 128-bit number that is checked before it touches a path. The finished file is checked by its first bytes (only photos and videos are let in), compared with the checksum the phone computed when it sent one, stored in the person's **own** Immich with their **own** session (so Immich's own rules for that person apply) and the pieces are deleted. A person may have at most `PHONE_UPLOAD_WAITING_MB` waiting and 200 unfinished files, one file may not exceed `PHONE_UPLOAD_FILE_MB`, and pieces nobody finished are deleted after `PHONE_UPLOAD_KEEP_HOURS` (48 by default). Tagging for a service happens only for a service the person sends to.
- **Co-hosts.** A co-host is another signed-in Immich user the owner chose by email. They act through the app, which uses the box's key: they never get the key or any access to the owner's library, and they do not see another person's other boxes. A co-host who only looks cannot see the link or the waiting files; one who manages cannot end the box or choose co-hosts. Every person's part is checked on the server for each action, and a box a person has no part in answers as if it did not exist.
- **Messages to the host** are data the app keeps itself: messages, names guests chose to give, and voice notes (checked by their first bytes to be audio, at most 2 MB each, at most 500 messages a box). They are served only to the owner and the co-hosts who manage the box, with a policy that lets nothing run, and the page can play them because the content security policy allows media from the app itself (`media-src 'self'`). They are in the data file, so in every backup, and they go when a revoked box is forgotten after a month.
- **A password on a drop box guards either the upload or the whole page**, chosen when the box is made. On **Upload** the page, its cover and its message are visible to anyone with the link, and only sending needs the password (messages to the host do not). On **The whole page** a guest without the password gets one answer: a page that asks for it, showing nothing of the box; the box's cover, colour, manifest, a guest's own uploads, the message form and the upload all answer as if they did not exist or refuse. The password is stored only as a salted PBKDF2 hash. A right password gives the guest's browser a cookie (`HttpOnly`, `SameSite=Lax`, `Secure` behind HTTPS, a week) holding a token made from the stored hash, which no guest can see, so it cannot be made up and stops working when the password changes. Wrong tries count against the guest like wrong uploads do. It does not cover a wall started for the box, which has its own link, nor the link of a shared album (that has its own password option in Immich), and a box with a password cannot take photos by email.
- **Sharing the photos back** uses Immich's own shared link, made with the owner's own session, so the box's key is not given any permission for it. The link is as private as how it is shared: it is a long random key, optionally behind a password, and has an end date. Immich ties downloads to showing a photo's details, so everyone with the link sees every photo's metadata. While a box has an open shared link, its closed link shows a page that leads to it; a box that shared nothing still answers like a link that does not exist.
- **A guest's ZIP** (only where the owner allows downloads) streams every original of the gallery through the app with the box's `asset.download` key, never stored: a guest may have one being made at a time, a box three at once, and each original also takes one of the eight places for downloads in the whole app, so it cannot overload Immich or the server. It is as private as the gallery (the same link and password).
- **The ZIP of a box** is made for the owner alone, with the owner's own signed-in session (so the box's key needs no new permission): the app reads each original from Immich and passes it on while the owner downloads it, keeping nothing. It is a plain `GET`, so a page of another site must not be able to start it: the app refuses a request the browser marks as coming from another site (`Sec-Fetch-Site`), and makes one ZIP of a box at a time.
- **What guests leave with a box** (hearts, names given with photos) is deleted at the end of the box's retention, once, and at once when the box is revoked; the photos are in the owner's library and are not touched. The key keeps `asset.view` (and `asset.download`) until the owner switches the gallery off or revokes the box, which deletes the key; the app only uses it for what the gallery and the wall may show.
- **Hiding and pinning** are done on the moderator page, by anyone who has the link, and change only what the app shows or puts in an album: a hidden photo is refused by the gallery, the pictures, the originals, the hearts, the wall and the guests' ZIP (it is not deleted, and the owner's own ZIP keeps it); a pinned one is kept by the best-of and goes first in the album of loved photos. A photo is named by its place in the box's list, and only a photo of that box can be marked.
- **A moderator link** is a link with 256 bits of randomness that lets whoever has it approve or reject the files that wait in one box, and nothing else. The page shows only that box's name and its waiting files (never the library, the link, the key, the log or the settings); a waiting file is asked for by its id and only if it is in that box's queue, and is served with a policy that lets nothing run; the key is read inside the app to store an approved file and never leaves it. It is made, renewed and ended by the owner alone, stops with the box, and is a different token from every other link of the box. The decisions are logged as "a moderator". Anyone who is given the link can use it from anywhere, so it is as private as how it is shared.
- **A gallery** (off unless the owner switches it on) lets everyone who has the link look at every photo the box kept, so it is as private as the link: give the box a password for private events (a password on **The whole page** covers the gallery's feed, pictures, hearts and downloads; on **Upload** it does not). It is built like the wall: a picture is asked for by its place in the box's list, never by an id in Immich, only a photo the box kept (and that was not taken back) can be asked for, and the key gets `asset.view` through the owner's own session. Downloads of originals additionally need `asset.download`, which the box's key has only while the owner allows downloads; at most eight go on at once in the whole app, and the original is streamed through, never kept. Hearts and the guest's name are data the app keeps: a heart is stored with a hash of the guest's secret (a random 128-bit cookie, `HttpOnly`, `SameSite=Lax`, `Secure` over HTTPS), never an address, at most 240 may be given or taken back an hour by one guest; a name, which a guest chooses to give, is cleaned (control characters, angle brackets and quotation marks removed, at most 40 letters) and kept only by a box that shows names. They go with the retention, when the owner chose one. With the key's `asset.view` the key could view any picture in the library; the app asks only for the box's own, and only the gallery, the wall and nothing else can ask.
- **A wall** is another way in with no sign-in, with a link of its own (256 bits, separate from the box's), which shows pictures of the box's photos and nothing else: a picture is asked for by its place in the box's list, never by an id in Immich, and only a photo the box kept (and that was not taken back) can be asked for. To fetch them the box's key gets `asset.view` through the owner's own session, and loses it when the wall stops; with that permission the key can view any picture in the library, so the app only ever asks for the box's own, and nothing but the wall can ask. Pictures are sent with a policy that lets nothing run and are kept in memory (at most 48 MB) for a short while.
- **A best-of** reads the pictures of a box's photos with the owner's own session, in the background, and writes only an album of the owner's. It stores for each photo its name, its verdict and a short reason (about a hundred bytes), never a picture, and deletes and changes nothing.
- **Handing the photos on** tags photos in the owner's library with a service's tag using the key the owner already made to send to that service, which has the permissions it always had. It adds no new power: the same could be done by tagging the photos in Immich.
- **Short links are easier to guess.** A short link is ten characters from a 31-letter alphabet (about 50 bits), against 256 bits for the long one. The per-guest limits and the box's own end date make guessing impractical, but they are not a lock: give a box that must stay private a password, or do not make a short link. Each way in can be ended on its own.
- **Guests' secrets.** A guest who may take back uploads holds a random 128-bit secret in a cookie (`HttpOnly`, `SameSite=Lax`, `Secure` over HTTPS). The server keeps only a hash of it, with the files it belongs to, so nobody else can list or delete them, and the app cannot tell which person a secret is.
- **A logo** is data, not code: a JPEG, PNG or WebP of at most 300 KB checked by its first bytes (never an SVG, never a page), served with a policy that lets nothing run and shown only in an `img`. A title is text, escaped like every other, at most 60 letters with no line breaks. The colour's contrast is worked out by the server (WCAG relative luminance) and written into the style sheet as a few checked hex values.
- **The look of the page** is data, not code: the colour is checked to be six hex digits before it goes into a style sheet, the cover must be a JPEG, PNG or WebP of at most 900 KB and is served with a policy that lets nothing run, and the page's language is one of those the app has. Shrinking happens in the guest's browser.
- **What the owner should still think about.** A link that is shared widely can be used by anyone who gets it; give it an end date, a size limit and, for a private event, a password, and revoke it when the event is over. Photos arrive in your library like any upload, so Immich's own checks (and your storage) apply.

## Notifications

Messages to `NOTIFY_URL` and `NOTIFY_FILE` name people, services and drop boxes, and say what went wrong. They go to the address you chose. A public ntfy topic is readable by anyone who guesses its name, so use a topic that cannot be guessed or a server you run. Mail goes to the addresses you list, through the server you name: its password is read from the environment, sent only over an encrypted connection and never logged. Addresses and tokens are never written to the log, and tokens in the file are read from the environment. See [Notifications](operations.md#notifications).

### Email to people

When mail to the people taking part is on, the data file holds, for each person who turned it on, their name, the address Immich shows for their account, their language and what they chose (removed when they turn it off; it is in backups meanwhile). Mail carries only what the person already sees in their Activity list, never photos, thumbnails or file names. Turning it on needs the person's own signed-in Immich session and the page's cross-site header; nobody can turn it on for someone else. Every mail has a link signed with a key derived from the store key (a link from another install, or a changed one, is "not valid"); opening the link only asks, and a POST to it stops the mail without a sign-in, as mail programs' one-click unsubscribe does. A person gets at most six mails an hour. Header and address values with line breaks are refused, and the text is escaped in the HTML part.

### Notifications on devices

A browser that allows notifications gives the app the address of its push service and two keys; the app keeps them sealed with the store key, and uses them only to send that person's notifications. The app calls only the push services of Google, Mozilla, Apple and Microsoft: the host of every address is checked when a device is added and again before each send, an address with another host, a port, an IP address or a login in it is refused, and redirects are not followed, so a person cannot make the server call an address of their choosing. Messages are encrypted for the browser (RFC 8291), so the push service sees only that a message was sent, when, and how large; they carry the same lines the person already sees on their page, never a photo, a file name or a thumbnail. Adding, changing or removing a device needs the person's own signed-in session and the cross-site header; nobody can touch another person's devices. The signing key (VAPID) is sealed in the data file; the contact it carries is visible to the push services.

### Event pools

In an event pool the same key **sends and receives**: a member's key can read and download the photos they tag, upload photos into their own library and tag them (the owner's receiving key gets the sender's permissions too). The permissions are the ones a sender that keeps its originals needs plus the ones a receiver needs, nothing that removes anything (a member's key can move copies to its owner's trash only when the administrator allows it for services in general, `RECEIVER_DELETE`). Joining is a consent: a pool refuses a join that does not carry the person's yes, in the app, not only in the page, and the question says that every photo they tag goes to everyone in the pool. **Whoever is in the pool gets the photos you tag**, so "anyone on this server" means anyone: use approval or an invitation to choose. A photo is handed to everyone but its sender, a copy carries the pool's `from/<name>` tag and the inbox tag but not the tag people send with, so it is not sent on, and if someone does tag a received copy it is handed on and each receiver's checksum check says "duplicate" (nothing new arrives). Nobody's original is changed or deleted. After a pool ends, tagged photos stay tagged and unsent.

### Photos by email

When the person who runs the app sets `MAIL_IN_HOST`, the app **logs in to a mailbox and reads the mail in it**, with credentials it holds in its environment (use a Docker secret for the password; `doctor` never prints it, and it is never written to the log). That mailbox should be used for nothing else, since the app deletes the mail it handles. The connection is encrypted (TLS or a required STARTTLS; unprotected only for a server on the same machine). The app asks a mail's size before reading it and leaves an oversized one unread; it decodes only mail addressed to a box of ours and keeps at most 25 MB of files from it (and at most 40 parts, nested at most four deep); it keeps **no address and no body**: the sender is turned into the same six-character one-way mark a guest has, the text of the mail is dropped, and only photos and videos (decided by their first bytes) are kept, under the box's own limits, approval and filing. Nothing is sent back to anyone. **Anyone who knows a box's address can send to it**, as with the link; mail servers do not prove who sent a message, so the mark is only a rough way to tell senders apart and the per-sender limits (30 requests in ten minutes, 300 files an hour) are easy to get round by forging "From" lines; the box's own limits (files, size, closing time) and its approval are what hold. A box with a password cannot have an address. Turning an address off at once stops the box taking mail.

### Frames

A frame's page has **no sign-in**: its long random link is its only protection, so it is as private as a drop box's link. Anyone who has it sees the photos that are in the album at that moment, in a size made for a screen (not the originals), until the link is ended or its date passes. The page carries nothing else (not the album's name, not who you are), is never indexed or cached, and sends no referrer. It never learns an Immich id: each photo has an opaque id made from the link and the photo, which means nothing in another frame, and the app serves a picture only for an id in the album right then. The frame has a key of its own, made with the owner's session, that can only look at pictures (`asset.view`) and list an album's photos (`asset.read`); it cannot download originals or change anything, but Immich cannot limit it to one album, so **the key could look at any of that account's pictures**; the app asks it only for the album's photos. The key is sealed like every other secret and deleted when the frame is ended. A frame past its date stops serving at once, but its key stays in the owner's account until they remove the frame (only their own session can delete it). Every refusal looks the same (unknown, ended and expired links all answer "not found").

**What a client room's link leaks, and what it cannot.** A client (anyone with the link, and the PIN if there is one) sees the title you gave, the pictures marked with your mark at preview size, their numbers, and nothing else: no Immich address, no album name, no photo id, no file name, no metadata, not the room's private name. They can write notes and choices into the room (plain text, bounded), and nothing more. They cannot reach an original before you release it, nor another visitor's choice in a room where each chooses alone. A person who photographs a marked picture off a screen has a marked picture. The marks, the PIN, the release and the key's permissions are all checked by tests (`internal/web/room_test.go`, `internal/hub/room_test.go`, `internal/mark`), and the whole flow, in a real browser on a phone-sized screen, by `TestRoom` and `TestRoomRounds` in the end-to-end suite.

A **client room** has the same shape as a frame: a long random link, a key of its own made with the owner's session that can only look at pictures (`asset.view`) and list an album's photos (`asset.read`), opaque photo ids made from the link and the photo (an id from one room means nothing in another, and a client never learns an Immich id), and the same answer for an unknown, paused-looking or ended link. The key cannot download an original: `asset.download` is added by the owner's own session when they release the photos (a room made to release by itself has it from the start, because nobody is signed in when a client sends a choice). Whatever the key may do, the app gives out an original only behind one check (`downloadPhotos`): the room is released and not past its days, the client's own choice was sent, the photo is in it, and in a named room the client is the one who chose; a test fails if any other code opens an original. As with a frame, Immich cannot limit a key to one album, so the key could look at any of that account's pictures and the app is what limits it. The PIN is stored salted and hashed. **A client only ever gets a marked picture**: the app fetches Immich's preview with the room's key, marks it (`internal/mark`, which reads JPEG, PNG and WebP with Go's own `golang.org/x/image`) and answers with the result; a preview that cannot be read or marked is an error, never the plain bytes, the cache holds marked pictures only, and a test fails if a room's files ask Immich for a picture anywhere but in the one function that marks it or if any route of a room returns the plain preview.

### Weekly digest

A weekly digest runs without anyone signed in, so it needs a key that can look at pictures and make an album and a shared link. It uses the service's own receiver key: when the owner turns the digest on (with their own session), the key gets `asset.view`, `album.read`, `album.create`, `albumAsset.create` and `sharedLink.create`, `sharedLink.read`, `sharedLink.delete` (only the ones it did not have), and turning it off takes away exactly those. Immich cannot limit a key to some of an account's photos, so **with those permissions the key could look at any picture in the owner's account**; the app only ever asks for the copies that arrived in that service during the week (taken from its own record of hand-overs), and the key stays sealed with the store key like every other. The digest makes an album of the owner's and a **view-only shared link that ends after 30 days** (a previous week's link is ended when the next is made, and when the digest or the service is removed). Anyone who has the link can see that album, with its dates and places (Immich allows downloads only with metadata shown); it is as private as the long link of a drop box. Nothing in the owner's library is changed or deleted, and the people who send to the service are not told about a digest; they cannot see it unless the owner shares the link.

### Action links

A link in a mail or notification (approve or decline a request, resume a service or your own sending) is a **key that opens exactly one door**: a random 128-bit value kept in the data file, made for one person and one action, valid for 24 hours, usable once, and cancelled with the other answer to the same request. It is made only for the person who can do the action (never for the one who asked, for other members, or for the administrator's channels) and only when that person has asked for mail or notifications. Opening a link shows what it will do and a button; only the button acts, so a mail scanner or a link preview that opens it does nothing. The button needs no Immich sign-in, which is the point (it works from a mail app) and the risk: **anyone who gets the link can use it once** before it expires, as with the drop box links, so mail and notifications should go to a mailbox and device only the person uses. The action is the same call the page's button makes, with the same checks, and the same Activity line is written. A request already decided on the page is not changed by an old link. The link is spent before the action runs, so two taps cannot both act; if the action is refused the person is told why.

## Who decides what

- **The sender** decides what happens to their own originals, when they join. The owner has no say over that.
- **The owner** decides who may send, and whether the service is listed or invitation-only.
- **Nobody** sees anyone's key, including their own.

## What is stored

- Without self-service ([Fixed accounts](fixed-accounts.md)) nothing is stored: all state lives in Immich as tags and workflows.
- With self-service, one SQLite file in the `handoff-data` volume lists who joined what. Every API key in it is encrypted with AES-256-GCM using `HANDOFF_STORE_KEY`. The app refuses to start if that key does not match the database.
- **Whoever runs the container and holds the store key can read those keys**, in the same way the person running Immich can already read the photos. This is the trust you place in the person who hosts it.
- The activity log keeps the last 500 events (who joined, left, asked, was approved, lost a connection), in the same file.
- For each person who turns them on: **email** (their name, the address Immich shows for their account, their language and their choice), each **device** they allow notifications on (the address of the browser's push service and its two keys, sealed with the store key), and the **one-tap links** made for them (a random value, for a day, once). Turning email off, removing a device or using a link forgets it. The app's push **signing key** is sealed in the same file.
- **Frames** and **client rooms** (the link, the album, the sealed key, the room's PIN as a salted hash), the state of each service's **weekly digest** (the last album and shared link, and which permissions it added to the key), an **event pool**'s end date, and a drop box's **mail code** are stored there too. The sender of a mailed photo is never stored.
- Drop boxes are stored there too: the name, message and limits, the link, the key (encrypted, like every key) and a log of up to 200 entries per box, its co-hosts, and counts for its summary (files per hour and which guests, by their mark). A revoked box and its log are forgotten after a month.

## What other people can see

Anyone signed in to Immich can open the page and sees the services that are **listed**, with the owner's name (not email). An owner sees the name and email of someone asking to send, and the names of their senders. Invitation-only services appear only to people who have the link; the link is only as private as how you share it, and **New link** revokes the old one.

An Immich **administrator** can also open the [administrator's page](admin.md), which lists every service, owner and member with their emails and the health of each connection, and can remove a service or a member. It never shows keys or photos, and removing something cannot revoke a key (Immich lets only its owner delete it; [why](admin.md#why-removal-cannot-delete-the-keys)). Who is an administrator is decided by Immich, for the signed-in person, each time.

## Protections in the app

- Immich's events carry a shared secret (`WEBHOOK_SECRET`); the app refuses one that is missing or shorter than 16 characters.
- The page accepts only people signed in to Immich. Every change needs a header that a page on another website cannot send, and each person is limited to 30 changes a minute. The one action that takes data away, the optional backup download, is off unless you switch it on and is limited further (see [Backups](#backups)).
- Pages are served with a strict content security policy, cannot be placed in a frame, and only load scripts and styles from the app itself.
- The metrics page needs the same secret.
- A photo is only removed after every receiver holds a verified copy (checked by checksum), and never while a connection is broken or a service has no healthy receiver.

## Backups

- A backup is a copy of the data file: every stored API key (encrypted with `HANDOFF_STORE_KEY`, which is **not** in the file) and names and emails in the clear. Treat it like the volume itself, and keep the store key separately.
- The app makes automatic backups into `/data/backups` by default. That is beside the data it protects, so point `BACKUP_DIR` at a second folder if you want to survive losing the volume.
- **The administrator's page can hand a backup to a browser, but only if you switch that on** (`HANDOFF_ADMIN_BACKUP_DOWNLOAD=true`). It is off by default because a stolen administrator session could then take a copy of the names and emails and the encrypted keys. When on, it needs a POST with the header a page on another website cannot send, a signed-in Immich administrator, and a confirmation in the page; it is limited to one download every 10 minutes for the whole app; each one is written to the recent events and sent to `NOTIFY_URL`; the copy is made in a private folder, removed as soon as it is sent, and marked `no-store`. The encrypted keys are useful only to someone who also has `HANDOFF_STORE_KEY`, which the page never shows. Details: [Download a backup from the administrator's page](operations.md#download-a-backup-from-the-administrators-page).

## The image you run

The published image is built by GitHub Actions from a tag of this repository, for amd64 and arm64, on a base with no shell or package manager (distroless). Each release is **signed** (cosign, keyless, tied to the release workflow), carries a software bill of materials and build provenance, and is checked by CI before it is published. [Releasing](releasing.md#verifying-an-image) shows how to verify an image yourself. The workflows pin every action by commit hash, and Dependabot proposes updates to the actions, the Go modules and the base images each week.
